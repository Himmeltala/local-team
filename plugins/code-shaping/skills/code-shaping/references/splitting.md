# 什么时候拆、怎么拆

拆函数的目的只有一个：把公共的、通用的逻辑抽出来，让多个调用处共用同一份。拆不是为了把代码切短。

## 先说不拆

- 一个函数写得很长，本身不是问题。只要它只服务自己这一条链路，就让它留在原地。
- 硬把一个大函数拆成若干小函数，调用处要准备一堆临时变量和参数，读的人还得来回跳着看。这样拆完可读性反而更差，不如不拆。
- 判断标准不是行数，是"这段逻辑还有没有第二个地方要用"。没有，就不动。

## 该拆的信号

- 同一段逻辑在第二个地方又要写一遍：这是拆公共函数最硬的理由。
- 一段逻辑与当前业务链路无关，而且换个功能也用得上，比如日期格式转换、编码转换、通用校验规则。
- 参数表越来越长：往往是把几个总是同进同出的数据拆散了传，考虑收成一个对象。
- 同段代码出现第二次：第二次先照抄，第三次动手抽，那时形态才看得清。

## 怎么拆

1. **拆公共的，不拆私有的。** 抽出来的函数要能被不止一处调用，名字取自它做的事，比如"把日期转成 `yyyy-MM-dd`"，而不是"第一步"。
2. **参数过长就传对象。** 参数超过三四个，或者这些参数总是成组出现，就定义一个入参对象，把字段收进去。调用处只传一个对象，函数内部按字段取用。
3. **抽出来的东西要能单独说清。** 给它一句话描述、一个名字、一段输入输出；说不清就先别抽。
4. **一次一小步。** 抽一点、跑一遍、再抽下一点；拆完行为不变是底线。

## 拆到什么程度

- 抽出来的函数只有一个调用处，也没有复用的可能，就退回去，留在原处。
- 抽出来的函数比调用处还长，或者参数比原来还多，说明拆错了位置，退回去。
- 为了缩短函数行数而拆，导致调用处多出一串临时变量、参数层层透传，说明这次拆不值得，改回原样。
- 抽象只能说出"以后可能有两个实现"，说不出现有的第二个，就不抽。
- 拆分的目标是让人改得动、用得上，不是让人看到更多层。

## 设计模式的位置

模式是给变化点用的，不是给"看起来专业"用的。

- 先找变化点：字段格式会变、算法会换、渠道会增加、规则会按客户不同。变化点在哪，模式就放哪。
- 没有变化点硬上模式，代价是多一层间接、多一批文件、少一半可读性。
- 简单写法能收住的需求，用简单写法；等第二个实现真的出现，再补接口也不迟。
