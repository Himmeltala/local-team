# 什么时候拆、怎么拆

拆不是把代码切碎，是让每一段只回答一个问题。

## 该拆的信号

- 名字说不清：`handleData`、`doProcess`、`updateInfo` 这类名字，通常装了三四件事。
- 读一遍记不住：函数长到要往回翻看开头，说明它一次交代了太多。
- 嵌套深：三层以上的 `if` 套 `for` 再套 `if`，先抽里层，再想扁平化。
- 参数多：参数表越来越长，往往是把几个不相干的数据硬塞进一个函数。
- 同段代码出现第二次：第二次先照抄，第三次动手抽，那时形态才看得清。
- 请求与业务混写：控制层里既取参数又算业务，服务层里既拼 SQL 又判权限。

## 怎么拆

1. **按职责切，不按行数切。** 先写出这段话在做的几件事，一件事一个函数，名字取自那件事。
2. **一层抽象一幕戏。** 同一个函数里，处理协议细节与处理业务规则不应同框；调用下层时不要顺手拆开下层的数据结构。
3. **先抽方法，再考虑抽类。** 方法级的拆分改动小、易验证；确实出现一组状态与行为绑在一起时，才升级成类。
4. **抽出来的东西要能单独说清。** 给它一句话描述、一个名字、一段输入输出；说不清就先别抽。
5. **一次一小步。** 拆一点、跑一遍、再拆下一点；拆完行为不变是底线。

## 拆到什么程度

- 抽出来的函数比调用处还长，或者参数比原来还多，说明拆错了位置，退回去。
- 抽象只能说出"以后可能有两个实现"，说不出现有的第二个，就不抽。
- 拆分的目标是让人读得顺、改得动，不是让人看到更多层。
- 常见退回信号：为了传参层层透传；为了一行代码包一层；接口比实现多。

## 设计模式的位置

模式是给变化点用的，不是给"看起来专业"用的。

- 先找变化点：字段格式会变、算法会换、渠道会增加、规则会按客户不同。变化点在哪，模式就放哪。
- 没有变化点硬上模式，代价是多一层间接、多一批文件、少一半可读性。
- 简单写法能收住的需求，用简单写法；等第二个实现真的出现，再补接口也不迟。
