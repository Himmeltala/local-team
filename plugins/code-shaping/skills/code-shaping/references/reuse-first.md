# 先找项目里已有的东西

新写一遍很容易，代价是同一个坑踩两次、同一个字段名两种写法、同一个功能三处实现。

## 动手前搜什么

- **同名字段与同类功能。** 按业务词搜一遍源码：区域、单位、状态、导出、分页，通常已经有实现。
- **公共层。** 工具类、`common` 或 `util` 包、基类、父接口、枚举、常量类。
- **框架机制。** 参数校验、鉴权、区域过滤、异常统一处理、事务、日志、定时任务、缓存、消息发送，项目里多半已经封过一层，直接接进去，别绕开。
- **前端机制。** 请求封装、拦截器、公共组件、全局样式变量、工具函数，先看 `utils` 与 `components`。
- **数据库约定。** 字段命名风格、公共字段（创建人、创建时间、软删除标记）、分页与排序的既有写法。

## 怎么判断该不该复用

| 情况 | 做法 |
|---|---|
| 现有函数正好干这件事 | 直接用，不改它的签名 |
| 现有函数差一两个参数 | 加可选参数扩展，注意别动现有调用方的行为 |
| 现有函数形似但语义不同 | 不要硬套；另写一个，名字把差异写出来 |
| 现有实现有缺陷 | 先按现有写法用，把缺陷记下来单独提，别在本需求里顺手改公共代码 |

## 复用不是硬凑

- 复用同一段**行为**，而不是复用同一段**代码形状**。形状像而语义不同，硬合并会让下次改动左右为难。
- 改公共代码要慎重：一处改动影响面大，先确认调用方，能不动就不动。
- 拿不准就问用户：这个功能项目里有没有现成的，我不确定，要不要我先搜一遍再动手。

## 通用工具的落点

新写的东西确实会被第二处用到时，放到公共层，并写清它的职责边界：只管什么、不管什么。放的位置比写法更重要，放错了下一个人找不到。
