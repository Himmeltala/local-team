# 先找项目里已有的东西

新写一遍很容易，代价是同一个坑踩两次、同一个字段名两种写法、同一个功能三处实现。

## 工程化的样子

一个工程像一座工厂。工厂分成很多部门，冲压车间只冲压，焊装车间只焊装，仓库只管存取，谁都不越界去干别人的活；部门之间靠明确的接口交接。代码也是这样：按行业通行的分层与分包来组织类和文件，每一层、每一个目录只做自己擅长的事。职责单一，别人才找得到它、改得动它、测得了它。

判断一个文件该放哪，先问两句话：这个文件负责哪一类事情？下一个要找这类事情的人会去哪个目录翻？答不上来，说明位置放错了。

## 动手前搜什么

- **同名字段与同类功能。** 按业务词搜一遍源码：区域、单位、状态、导出、分页，通常已经有实现。
- **公共层。** 工具类、`common` 或 `util` 包、基类、父接口、枚举、常量类。
- **框架机制。** 参数校验、鉴权、区域过滤、异常统一处理、事务、日志、定时任务、缓存、消息发送，项目里多半已经封过一层，直接接进去，别绕开。
- **数据库约定。** 字段命名风格、公共字段（创建人、创建时间、软删除标记）、分页与排序的既有写法。

## 后端怎么分层

Java 工程一般按职责分层，从上到下依次是：

- **接口层**（`controller`、`web`、`api`）：只负责接收参数、校验、调用服务层、包装返回。不写业务计算，不拼 SQL，不判复杂权限。
- **服务层**（`service`）：业务编排与事务边界。一个方法讲清一件事，跨表的组合逻辑放在这里。
- **数据访问层**（`dao`、`mapper`、`repository`）：只做数据存取，不掺业务判断，不处理展示格式。
- **实体与模型**（`entity`、`model`、`po`）：与数据库表一一对应，不放业务方法。
- **传输对象**（`dto`、`vo`、`bo`、`query`）：入参对象、出参对象、内部传递对象各归各的包；接口出入参不用实体直接顶替。
- **基础设施**（`config`、`util`、`common`、`exception`、`constant`、`enum`）：配置、工具、公共常量、统一异常，各自独立成包。
- **横切能力**（定时任务、消息监听、外部系统适配）：单独成包，不与业务服务混在一起。

分层的硬约束是单向依赖：上层可以调用下层，下层不能反过来引上层。接口层不出现 SQL，数据访问层不出现业务规则。违反这条，工厂就变成了谁都干谁都不专。

同一业务模块下，也可以采用"按功能分包、包内再分层"的组织方式，即 `模块/controller`、`模块/service`、`模块/mapper`。无论哪种，同一个业务概念的类都放在同一处，不要按类型散落到全工程。

## 前端怎么分包

Vue 或普通 JavaScript 工程一般按用途分目录：

- **页面**（`views`、`pages`）：一屏一个目录，页面文件只做装配与交互，不堆放通用逻辑。
- **组件**（`components`）：可复用的界面单元。基础组件放 `components/base` 或 `common`，业务组件放 `components/业务名`；只被一个页面使用的，留在页面目录内，不要上提到全局。
- **接口**（`api`）：一个业务模块一个文件，请求地址与参数在这里定义，页面不直接散写 `axios` 调用。
- **工具**（`utils`）：纯函数，不依赖组件状态。日期、金额、字符串、树结构这类处理放这里。
- **组合式函数**（`composables`、`hooks`）：复用带状态的逻辑，如列表分页、弹窗开关、表单校验。
- **状态**（`store`）：全局共享状态，按业务模块拆文件；只在本页使用的状态不进全局。
- **路由**（`router`）：路由表与守卫，不放业务代码。
- **静态资源**（`assets`）：图片、字体、图标，按类型或业务分子目录。

一个 `.js` 文件只承担一类职责。工具函数、接口定义、组件配置、路由表不要塞进同一个文件。

## 样式文件怎么放

- **全局样式**（`styles`）：重置样式、主题变量、公共原子类、第三方组件覆盖。全局样式里不写具体页面的业务色值与布局。
- **变量与主题**：颜色、字号、间距、圆角统一用变量文件定义，页面与组件只引用变量，不写死色值。
- **公共组件样式**：与组件同目录，跟随组件走；不要为了复用样式把组件的样式提进全局。
- **页面样式**：留在页面自己的样式块或配套的 `.css`、`.scss` 文件里，加作用域限制，避免污染别的页面。
- **命名**：沿用工程既有的命名方式（BEM、模块前缀、CSS Modules 等），新加的样式与已有风格保持一致。

## 怎么判断该不该复用

| 情况 | 做法 |
|---|---|
| 现有函数正好干这件事 | 直接用，不改它的签名 |
| 现有函数差一两个参数 | 加可选参数扩展，注意别动现有调用方的行为 |
| 现有函数形似但语义不同 | 不要硬套；另写一个，名字把差异写出来 |
| 现有实现有缺陷 | 先按现有写法用，把缺陷记下来单独提，别在本需求里顺手改公共代码 |

## 复用不是硬凑

- 复用同一段**行为**，而不是复用同一段**代码形状**。形状像而语义不同，硬合并会让下次改动左右为难。
- 改公共代码要慎重：一处改动影响面大，先确认调用方，能不动就不动。
- 拿不准就问用户：这个功能项目里有没有现成的，我不确定，要不要我先搜一遍再动手。

## 新东西放哪

新写的东西确实会被第二处用到时，按上面的分层放进去，并写清它的职责边界：只管什么、不管什么。放的位置比写法更重要，放错了下一个人找不到。

- 业务无关、可跨模块调用：放公共层（后端 `common`、`util`，前端 `utils`、`composables`）。
- 只服务某一业务模块：放该模块自己的目录内，不要上提到全局。
- 一个类或文件承担了两种职责：按部门拆开，各放各的位置，不要为了省文件而混放。
- 新增文件后，回头检查一次依赖方向：是否出现下层引用上层、工具函数反向依赖业务。
