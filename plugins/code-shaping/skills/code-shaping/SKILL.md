# 写之前先想三件事

1. **这段东西该待在哪。** 项目里是不是已经有现成机制、公共函数或基类能接；放哪一层，叫什么名字。
2. **它干几件事。** 超过一件就先把职责拆开，再谈怎么写。
3. **这是第几次出现。** 第一次照写，第二次留意，第三次动手泛化。

细则分三份：拆法见 `references/splitting.md`，找现成的见 `references/reuse-first.md`，其余条目见 `references/thinking.md`。

## 判断清单

以下是判断角度，不是硬性规定。真按条款写代码反而别脚。

- **复用优先。** 动手前搜一遍项目：公共函数、工具类、基类、注解、拦截器、统一入口。写第二遍之前先确认它真的不存在。
- **一个函数一件事。** 读名字说不清它干什么，就是混了两件事，先拆职责再拆代码。
- **过长就拆。** 行数多、嵌套深、参数多、分支多，任一条明显就考虑拆。不看单一数字，看"读一遍记不住"这件事。
- **胶水代码要泛化。** 满屏的字段搬运、DTO 互转、条件堆砌，抽成映射表、批量处理或统一入口。
- **模式用得其所。** 模式的价值是把变化点隔离出来；说不出变化点在哪，就不要上模式。
- **不许过度抽象。** 只有一处用到的不抽；抽象出来的东西比调用处还长就退回；抽象要能说出第二个使用方；"将来可能要用"不算理由。
- **顺手不越界。** 本次动到的部分顺手理顺，不做大范围重构；大重构单独提，别夹在需求改动里。

## 反面清单（症状自查）

- 方法读到一半忘了开头，得往回翻。
- 同一段字段取值在五个地方各写一遍。
- 为一个实现抽了一层接口，另外两个实现一直没出现。
- 工具类里塞业务逻辑，或者业务代码里直接拼 SQL、发消息。
- 为了"复用"，把两段不相干的东西硬合成一个函数，参数越加越多。
- 改一处需求要动五个文件，而且每个文件都改得差不多。

## 与其它插件的分工

- 注释怎么写、留什么删什么，见 `comment-trimming` 插件。
- 中文表达与术语，见 `chinese-writing` 插件。
- 代码写完发现现象不对，走 `bug-tracing` 插件，不在这里猜。
