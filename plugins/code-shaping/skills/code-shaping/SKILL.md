# 写之前先想三件事

1. **这段东西该待在哪。** 项目里是不是已经有现成机制、公共函数或基类能接；按分层放在哪一层、哪个目录，叫什么名字。
2. **有没有第二处要用。** 只有会被多处调用的逻辑才抽公共函数；只服务自己一条链路的，留在原地。
3. **参数长不长。** 参数超过三四个，或几个数据总是成组出现，收成一个入参对象。

细则分两份：拆法见 `references/splitting.md`，找现成的与分层分包见 `references/reuse-first.md`。

## 判断清单

以下是判断角度，不是硬性规定。真按条款写代码反而别扭。

- **复用优先。** 动手前搜一遍项目：公共函数、工具类、基类、注解、拦截器、统一入口。写第二遍之前先确认它真的不存在。
- **拆只为公用。** 函数写得长本身不是问题，不要为了缩短行数硬拆。同一段逻辑要在第二处用到，才抽成公共函数。硬拆导致调用处堆临时变量、来回跳读，不如不拆。
- **参数过长传对象。** 参数表越来越长，说明几个总是同进同出的数据被拆散了传，定义一个入参对象收进去。
- **分层分包各司其职。** 按行业通行的分层放类和文件：后端接口层不写 SQL、数据访问层不写业务；前端页面、组件、接口、工具、样式各归各的目录。像工厂分车间，每个部门只做擅长的事。
- **胶水代码要泛化。** 满屏的字段搬运、DTO 互转、条件堆砌，抽成映射表、批量处理或统一入口。
- **模式用得其所。** 模式的价值是把变化点隔离出来；说不出变化点在哪，就不要上模式。
- **不许过度抽象。** 只有一个调用处且没有复用可能的，不抽。抽出来的函数比调用处还长、参数比原来还多，退回原处。"将来可能要用"不算理由。
- **顺手不越界。** 本次动到的部分顺手理顺，不做大范围重构。大重构单独提，别夹在需求改动里。这里的「顺手」只管代码结构（拆分、抽取、复用），范围不越出本次改动。注释的清理范围另有规定，按 `comment-trimming` 插件是整文件——两者不冲突，各管各的。
- **不适用的改动。** 机械改名、格式化、注释清理、纯配置调整不用套这份清单，按对应规范或工具做。

## 反面清单（症状自查）

- 同一段字段取值在五个地方各写一遍，同一段逻辑在第二处照抄第三遍。
- 为一个实现抽了一层接口，另外两个实现一直没出现。
- 为了缩短函数行数而拆，调用处多出一串临时变量和逐层透传的参数。
- 函数参数一长串，调用时必须照着参数顺序数位置。
- 工具类里塞业务逻辑，或者业务代码里直接拼 SQL、发消息。
- 页面里直接写请求地址与 `axios` 调用，或把页面专用样式写进全局样式。
- 为了"复用"，把两段不相干的东西硬合成一个函数，参数越加越多。
- 改一处需求要动五个文件，而且每个文件都改得差不多。

## 与其它插件的分工

- 注释怎么写、留什么删什么，见 `comment-trimming` 插件。
- 中文表达与术语，见 `chinese-writing` 插件。
- 代码写完发现现象不对，走 `bug-tracing` 插件，不在这里猜。
