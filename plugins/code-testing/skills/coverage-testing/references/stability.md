# 连跑验稳与偶发失败排查

## 为什么必须连跑三轮

带线程、带网络、带定时任务的用例，单次全绿说明不了什么。跑三轮是为了把"偶尔才红"的那些挑出来。凡是这三轮里红过一次的用例，都得查清根因再报完成——没人会替你在上线前一天发现它。

跑的时候看总耗时有没有异常波动。某一轮明显慢，通常是某个用例在等超时。

## 偶发失败的三类根因

### 一、断言点选早

最常见的一类。断言写在了"事件已完成"之前，而信号只代表前一步做完了。

典型：断言"归档目录里有 2 个文件"，而这条断言紧跟在"对端收到字节"之后——字节到达对端是接收线程干的，文件迁移是发送返回后干的，两者谁先谁后不定。

改法：两个信号都要等时，**分别等两个条件**，别用一个代替另一个。规则本身见 SKILL.md 的硬规矩一。

### 二、并发顺序本来就不保证

断言了两个并发动作的先后，而代码从没承诺过这个顺序。比如事件先丢进线程池再分发，池里有多个线程，连着两次投递的顺序就可能颠倒。

改法：先判断被测代码有没有承诺顺序。承诺了，写清是哪个承诺、按承诺断言；没承诺，就别断言顺序——要么串行发（发一条等一条到达），要么只断言集合内容不比较顺序。**改了断言不等于问题解决了**：如果业务上需要顺序，那就是产品缺陷，按缺陷报。

### 三、测试自己造的极端条件太慢

为了让某个分支触发而压小的缓冲、灌进去的十几 MB 报文、调短的超时，会把正常路径的用例一起拖慢，甚至拖过超时。

典型：为了让"写超时"能触发，把对端接收缓冲压到 1 KB；结果同一个假对端在正常用例里也这么大窗口，几十 MB 的报文传不完。

成因与规避见 `fake-peer.md` 的「只连不读怎么造」。

## 排查顺序

1. 看失败断言的消息与期望值、实际值，先分清是"差一个"还是"差一半"。"差一个"通常是时序，"差一半"通常是并发或截断。
2. 打开测试报告里的输出文件（surefire 会重定向测试期日志），按时间线看那一刻各个线程在干什么。
3. 反复单跑这条用例十次，确认是可复现还是纯偶发。偶发也照样得查，只是不用急着改。
4. 定位到根因后，改法要么改测试（断言点、等待方式、极端条件的范围），要么报产品缺陷。别用"重试三次"把测试改绿。

## 报完成的门槛

- 全绿，且连跑三轮都是全绿。
- 每一条用例都能说清在防哪个回归。
- 未覆盖的行有清单和理由，不是"尽力了"。
- 跑一轮的耗时能接受（几十秒量级，不是几分钟）。
