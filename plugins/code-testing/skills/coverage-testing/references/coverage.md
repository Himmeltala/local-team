# 量覆盖与按未覆盖行补测

## 先拿基线，再补

别一上来就按感觉补用例。先跑一遍拿基线（行覆盖、分支覆盖、方法覆盖三个数），再看未覆盖行清单，逐条决定补还是不补。基线能省掉一半无用功：很多"以为没覆盖"的地方其实早有用例。

报告里要看的是逐行的清单，不是总数。总数只用来对目标，补测要照着行号来。

## 未覆盖行分三类

拿到清单后逐条归类，别一律补：

**第一类，能造出来的，补。** 参数校验失败、catch 分支、边界值、空集合、上限与下限。这类占多数，也最容易补：触发条件就在代码里写着。

**第二类，环境故障，记账不补。** 写文件失败、读文件失败、删除失败、磁盘满、权限不足。要造这些得把目录或文件权限改坏，而 CI 或本地一旦以 root 跑，权限根本不生效，用例会假绿——比不覆盖更糟。这类写进文档：哪些行没覆盖、为什么、上线后怎么人工验。

**第三类，防御性不可达，记账，并考虑删。** 有些分支在生产路径上到不了，比如"连接对象已置空后再取输入流失败""线程池已关闭后再提交"。写它们时的假设已经不成立。处理办法二选一：确认真的到不了就删掉；拿不准就留着，但在文档里写明是防御代码。

## 分支覆盖比行覆盖更值得看

行覆盖到 90% 但分支覆盖只有 70%，说明很多 `if` 只走了 true 这一边。补测时优先补分支：一个判断的两种结果都要有用例，尤其别漏"解析失败""校验不通过"这一侧。

## 反射能不能用来覆盖

能，但有条件。当某个分支在生产路径到不了、又确实值得钉住（比如"线程池被关闭后再推送不应抛异常"），可以在测试里用反射把内部状态改成那个样子，再断言行为。写法：

```java
Field field = Target.class.getDeclaredField("writer");
field.setAccessible(true);
((ExecutorService) field.get(target)).shutdownNow();
```

判定标准是"这个分支是产品行为的一部分吗"。是就用反射钉住，不是（纯 IO 故障）就走第二类记账。用反射的地方在测试方法上加一行注释说明意图，别让后来人以为是 hack。

## 别为覆盖率写假测试

三种典型的假测试，都不要：

- 只调用不断言。跑过就算覆盖，出了回归也发现不了。
- 断言恒真。`assertTrue(size() >= 0)` 这种，等于没断言。
- 把测试写死到实现细节。断言私有方法的调用次数之类，重构必红。

补每一条用例时问自己一句：**它在防哪个回归？** 答不上来的删掉。覆盖率是手段，不是目的，90% 这个数只是"漏得不多了"的近似。
