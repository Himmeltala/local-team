# 进程内假对端

## 为什么放进程内

放进程内不是图省事，是为了让测试能直接观察和操纵对端：

- 断言要拿到对端收到的字节，进程内直接用对象引用，进程外要么读日志文件、要么再开一个查询接口。
- 要造"对端断开""对端不读"这类场景，进程内改一个字段就切过去了，进程外要 kill 再重启。
- 测试结束后要保证不留残余进程。

代价是假对端与测试共用 JVM，它自己的 bug 也会影响测试。取舍：假对端写简单点，别在它里面写业务逻辑。

## 五个必备能力

| 能力 | 用来测什么 | 实现要点 |
|---|---|---|
| 接受连接 | 基本链路 | 真开监听端口，每个连接起一个读线程；断开一个连接不影响其他连接 |
| 累积收到的字节 | 内容与长度断言 | 所有连接的字节写进同一个线程安全缓冲；跨重连也累加，这样断言"重连后继续推送"才成立 |
| 记连接次数 | 重连行为 | 计数器，断言 `连接次数 >= 2` 证明客户端真的重连了，而不是原地死等 |
| 主动断开 | 断线重连、失败留原地 | 把所有当前连接关掉；客户端应当在若干秒内重连 |
| 只连不读 | 写阻塞、写超时 | 接受连接但不起读线程，并把接收缓冲压小（见下） |

可选第六个能力：**主动回数据**。每接受一条连接就回一段固定字节，用来验证客户端的读线程确实在把对端数据读走，而不是把数据堆在接收缓冲里。

## 只连不读怎么造

要让写方真的阻塞，得让对端的接收窗口关掉。做法：接受连接后不起读线程，并把这个 socket 的接收缓冲压到 1 KB 量级，然后发一条远大于两端缓冲之和的报文（十几 MB 起步）。发送方很快就会撞上写超时。

两条纪律：

- **别把压小接收缓冲的逻辑写进所有连接**。压小之后大报文的吞吐会掉几个数量级（小窗口配延迟确认），正常路径的用例会被拖到超时。只在"只连不读"这一种模式下压。
- 模式判断与"是否起读线程"要用**同一个局部变量快照**，别在两个分支里各读一次标志位，否则会出现"压了小窗口却还在读"的半截状态。

具体到 Java 的写法与副作用，见 `java-testing` 技能的 `references/async-and-sockets.md`。

## 与 mock-testing 的共存

同一条链路可能两边都要用：

- 手工阶段用 mock-testing 起独立模拟服务，摸清真实对端发的字节形状与应答规则。
- 固化阶段把这份契约搬进进程内假对端，写成用例。

搬的时候注意：**契约仍然从被替换方的源码抄**，不要从模拟服务的实现抄——模拟服务当初就是照源码抄的，隔一层容易抄错。

## 端口与收尾

- 端口取 `0`，由系统分配，从监听对象上读回真实端口。别写死端口。
- 需要"先知道端口、稍后再起服务"的用例（比如先验证对端不在时留在原地，再起对端验证补推），先取一个空闲端口再关掉，把这个号留给后面的服务。这里有极小的被抢占风险，能接受。
- 假对端实现 `Closeable`，用例里用 try-with-resources 包住；进程内假对端不关会占着端口，影响后续用例。
