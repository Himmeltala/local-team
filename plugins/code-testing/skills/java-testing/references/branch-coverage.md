# 用反射覆盖防御分支

## 什么时候值得用

有些分支在产品里是防御性质，正常路径永远走不到，但确实存在：线程池已被关闭之后再提交任务、连接对象已置空之后再取流、写线程已经退出之后还要 join。这类分支的代码是对的，只是没有触发器。

判断标准：**这个分支是不是产品行为的一部分？**

- 是（比如"停机过程中并发推送不应抛异常"）——用反射把状态改成那个样子，断言行为，钉住。
- 不是（纯 IO 失败：磁盘满、权限不足）——记账不补。为造这类场景要改文件权限，跑在 root 下会假绿，比不覆盖更糟。

## 写法

```java
private static ExecutorService writerPool(PushTcpClient target) throws Exception {
    Field field = PushTcpClient.class.getDeclaredField("writer");
    field.setAccessible(true);
    return (ExecutorService) field.get(target);
}

@Test
void 写线程池被关闭后推送返回失败不抛异常() throws Exception {
    client = start(third.port());
    writerPool(client).shutdownNow();

    assertFalse(client.send(new byte[]{1}), "写线程池没了应返回失败而不是抛异常");
}
```

要点：

- 取字段名要与源码一致，字段改名测试就红——这是可接受的代价，比覆盖不到强。
- 反射代码抽成小工具方法放在测试类底部，别散在用例里。
- 用例名直接写"什么状态下会发生什么"，读名字就知道这条在测什么。
- 测试报告里把这类用例单独认出来（名字里带"被关闭后""被单方面"这类词），将来有人重构内部结构时知道要一起改。

## 反射改状态与并发

反射拿到的对象通常正被别的线程使用。改状态前先确认被测对象此刻是静止的：连接已建立、没有在途请求。改完之后立即断言，别中间夹 `sleep`，否则被别的线程改回去就白测了。

## 不可达分支要不要删

测不出覆盖率的防御分支，最终要在"删掉"与"留着"之间选一个：

- 留着：多一层保险，代价是覆盖率报告上永久留几个缺口。在文档里写明哪几行没覆盖、为什么。
- 删掉：代码更干净，但如果当初写它的假设将来变了（比如换成别的连接实现），少一层兜底。

拿不准就留着并写明。删代码比留代码风险大，特别是那种"只在一个很窄的时序里生效"的兜底。
