# Mapper XML 与 SQL 注释做法

MyBatis mapper 在各模块的 `src/main/resources/mapper/*.xml`。这里的注释承载的业务口径比 Java 侧还多，清理时要更保守——一个中等规模的 mapper 文件动辄有几十处 `--` 注释。

注意区分源文件与构建产物：`target/classes/mapper/*.xml` 是编译时复制的副本，改注释只改 `src/` 下的源文件。

## 语法前提

两种注释形式：

- SQL 行注释 `-- ...`，写在 `<select>` / `<update>` 等 SQL 文本内部
- XML 注释 `<!-- ... -->`，写在 XML 结构层

两个硬性限制，容易踩：

- XML 注释内部**不允许出现 `--`**（XML 规范禁止）。`<!-- 处理 -- 分隔 -->` 是非法 XML，解析直接报错。
- `--` 注释不能嵌套，也不能写在字符串常量里。
- `--` 后要跟空格。`--注释` 在部分 SQL 解析器下会被当成运算符。

## 保留：这些是负载信息

逐字取自存量项目的 mapper：

```sql
-- 虚谷库不支持按聚合表达式排序，须用 SELECT 别名
```

```sql
-- 行转列按小类统计：虚谷库 LEFT JOIN 下 COUNT 会退化成 COUNT(*)，空区域记成 1，须用 SUM
```

```sql
-- 2. 智能终端业务告警：DEVICE_TYPE=60 时取图片与视频地址
```

这三条分别写清了数据库引擎的坑、聚合口径的陷阱、以及 UNION 分支取哪类数据。删掉任何一条，后来人都会照着直觉改回去然后踩同一个坑。

**一条一行，最多两行**（数值出自 `chinese-writing` 插件的篇幅标准）。上面第二、三条原来带着几十字的括号补充，压成一行照样拦得住误改——留结论与关键字（库名、字段、后果），删掉推导过程与举例。压不下去又丢不得的，报给用户定，不要写成长注。

判断标准与新项目无关：**凡是记录了"不这么写就出错"的注释，一律保留**，无论它提到的是哪个库、哪张表。

**编号前缀不要删。** `-- 1.` `-- 2.` `-- 3.` 在大段 UNION 查询里是导航标记，指名每个分支的数据范围。这和 Java 里 `// 第一步：校验` 那种复述式标语不同：后者编号后面跟的是废话，这里编号后面跟的是分支语义。

## 删除：这些是噪音

```sql
-- 查询列表
SELECT ... FROM tb_alarm_info

<!-- ==================== 告警查询 ==================== -->

-- TODO 🚀 优化
```

- 复述下一条语句的注释
- XML 注释做的横幅装饰
- emoji 与装饰符号（加号 `+`、乘号 `×`、箭头、线条、几何符号、`★✓✗`、emoji 都不要；对照表以 `chinese-writing` 插件的符号规则为准）
- 被注释掉的旧 SQL 片段

## 判断标准

与 Java 侧同一套：删掉这行，后来人会误改或看不懂吗？会就留；留下的话，一行写得完吗？写不完就压成一句。

SQL 侧因为无法用类型和命名表达意图，倾向更保守——拿不准就留；但"留"只放宽删不删，不放宽长短，压不下去又丢不得的报告给用户。

## 边界

- 不改 SQL 逻辑。裁剪只碰注释与空行。
- 不重排 XML 缩进，不调整标签顺序。
- 不把 `--` 注释改成 XML 注释，或反过来。它们的作用域不同，换了位置会变语义。
- 动态 SQL 标签（`<if>` / `<foreach>` / `<choose>`）里的注释保留原位置——挪出去就失去了"只在这个分支生效"的含义。
