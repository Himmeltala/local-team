# 踩坑清单，按症状查

## 桩起不来

**端口已被占用**。症状：启动报地址已被占用。本机常见嫌疑人：开发服务器、nginx、IDE 里跑着的同一个服务。做法：起之前先查端口，占用就先确认是不是自己上一次没停干净。起停脚本里加端口预检，见 `examples/sim_run.sh`。

**端口通了但起来的是别人的进程**。症状：请求打到别的服务上，返回内容莫名其妙。做法：就绪探测不能只看端口有没有人听，要比对刚起的进程号与端口上的进程号一致。确认之后再往下走。

**在错误的目录起服务**。症状：静态资源 404、模板找不到。做法：桩里显式打印工作目录与静态根目录，日志里能一眼看出。

## 请求到了但结果不对

**路径前缀被代理剥掉**。症状：桩返回兜底 404。做法：确认代理的 rewrite，按剥完之后的路径注册路由。

**字段名或格式不一致**。症状：桩收下请求但解析失败，或被测方读不到返回字段。做法：回到 `references/contract-first.md`，拿真实报文逐字段比对。

**对端按序号去重**。症状：第一次测通过，第二次同样的包完全不生效，日志显示"指令已处理"。做法：每次换一个序号或标识（改 tag、换 uuid），别拿同一个包反复测。

**单连接服务互相顶替**。症状：脚本一跑，界面就断；界面一开，脚本收不到消息。做法：确认服务端是不是只保留最新连接，是的话两边轮流开，别同时开。

**系统代理拦掉本机请求**。症状：连 `127.0.0.1` 却报代理相关错误或超时。做法：脚本里显式关掉环境代理，Python 的 `requests` 用 `sess.trust_env = False` 加空 `proxies`，与生产代码保持一致。

## 链路静默失败

**成功码与实际不符**。症状：桩返回 200，但被测方判的是返回体里的业务码。做法：把被测方的成功判据从代码里找出来，桩按它满足。

**判断分支提前 return**。症状：日志里只有入口那一行，之后什么都没有。做法：临时加打印，把判断依据的实际取值打出来，见 `references/verify-and-cleanup.md`。

**异常被吞**。症状：什么都不发生，也没有报错。做法：查相关 catch 块，临时加打印再跑。

**界面在跳不代表通了**。症状：数字在动，但业务动作没发生。做法：用观察器直接看报文，别信界面。

## 结果对但不可信

**产物比源码旧**。症状：改了代码却没有任何变化。做法：重新构建产物；构建产物里缺资源文件（只打进了 class）也是常见情况，验证一下产物里该有的资源在不在。

**测的是桩的返回，不是被测方的处理**。症状：桩返回什么就报什么结论。做法：第三层必须落到产物上，库里字段、文件内容、广播报文，看到才算。

**共享文件被就地改了**。症状：收尾时发现共享盘配置变了，影响别人。做法：一开始就用私有副本加参数指向，收尾用 md5 核对。

## 脚本自身的坑

**管道提前退出导致误判**。症状：`cmd | grep -q` 之后把 `cmd` 的失败误判成"内容里没有这一项"。做法：先把输出整体取到变量里再匹配，别让管道下游提前退出。

**日志 tail 没有起点**。症状：脚本起来就刷屏，关键行被冲走。做法：tail 时记录行号偏移，只打增量，并按关键字正则过滤。

**判断"服务已就绪"用固定等待**。症状：机器慢的时候时好时坏。做法：轮询探测（探端点或探日志关键字），配超时上限。

**清理不干净**。症状：下一轮测试被上一轮的进程干扰。做法：写 pid 文件，`stop` 子命令按 pid 停，并核对端口已释放。
