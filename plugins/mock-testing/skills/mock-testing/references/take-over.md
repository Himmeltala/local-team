# 接管：把被测端的地址指到桩上

桩起好了，被测端仍然打到真地址，这轮测试就是白跑。接管手段按影响面从小到大选，能不碰文件就不碰文件。

## 四种手段，从轻到重

### 1. 脚本自己的命令行参数

影响面最小。给桩或给造数脚本加 `--target`、`--backend` 一类参数，默认值指向真地址，测试时显式传桩的地址。

适用：自己写的造数脚本、上报脚本、观察器脚本。

### 2. 应用的启动参数

不改任何文件，只在启动命令上加覆盖项。Spring Boot 形如 `--rootPath.cachePath=/tmp/xxx`，覆盖 `application.yml` 里的同名键。命令行参数优先级高于配置文件，所以能覆盖。

适合覆盖的：路径类配置、开关类配置、超时阈值。

启动命令要落进起停脚本，别只留在终端历史里，否则下次没人知道当时覆盖了什么。

### 3. 前端开发代理的 target

改 `vite.config.js` 一类代理配置里的 `target`。注意三件事：

- **rewrite**。代理带 rewrite 时会剥掉路径前缀，`/api/inout/xxx` 落到后端是 `/inout/xxx`。桩的路由要按剥完之后的路径写。
- **changeOrigin**。开了会改 Host 头，靠 Host 判断的桩要留意。
- **同名前缀的其它规则**。同一份配置里可能还有其它前缀指向别的服务，改之前把整段读完，别只改一行。

改前把原值记下来。

### 4. 应用配置文件

影响面最大，优先级最低。改之前先问自己前三种办法为什么不行。

改共享盘或生产环境的配置文件时，一律不就地改：复制一份到临时目录，只改副本里需要的那一两个键，再用启动参数把路径指到副本。共享文件保持只读，收尾时用 md5 核对没被动过。

## 地址决策链要摸清

有些程序读地址不是读一个配置，而是按优先级链：先读运行时配置文件，读不到才回退启动参数或默认值。这种链路下，只改一处可能根本不生效，因为另一处优先级更高。

摸清顺序的办法：从代码里找解析地址的那个类或函数，看它按什么顺序取值。起桩之后用桩的请求日志反证：桩收到请求，说明接管生效；桩一条没收到，说明流量走了别的地址，此时回退查优先级链。

## 改动记录表

每改一处就记一行，收尾照着还原：

```
文件/参数：<路径或参数名>
原值：<改之前的值>
新值：<桩的地址或副本路径>
重启生效方式：<重启进程 / 重跑构建 / 热更新>
```

## 还原

- 配置文件类改动用版本控制还原（`svn revert` / `git checkout --`），比手工改回去可靠。
- 启动参数类改动只存在于启动脚本里，收尾时确认脚本里没留下测试用的覆盖项。
- 共享文件用 md5 核对，结果写进结论。
- 前端代理改动如果是有意长期保留的（指向本机服务便于开发），也要在结论里写明，别让下一个人以为是漏改。
