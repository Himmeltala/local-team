# 验证与收尾

桩起来了、请求也发了，不等于链路通了。只有第三层通过才算测到。

## 三层验证

### 第一层：桩活着

- 端口在听：`ss -lntp | grep <端口>` 或 `lsof -i:<端口>`。
- 桩的请求日志打出了这一次请求，方法与路径对得上。
- 一条请求都没到，先查接管（见 `references/take-over.md`），不要先怀疑桩。

### 第二层：被测端认账

在被测端日志里找该链路的关键字，并且看顺序。把关键字的顺序写下来当基线，例如：收到请求、校验通过、转发出站、对端已返回、状态已回写。顺序乱了说明中间某步分支没走。

排查时抓这几类关键字：入口方法名、分支日志、异常堆栈的类名、出站请求的地址。

### 第三层：落地产物

链路终点到底改了什么，去核对实物：

- 文件：内容、版本号、大小、md5。
- 接口：状态码、返回体字段。
- 数据库：目标字段的值。
- 消息总线：广播出去的报文原文（用观察器抓，别只看界面数字跳动，界面可能由另一条通道驱动）。

## 界面不能当唯一依据

界面上数字在跳，只能说明某条通道活着。链路里的判断、投递、落库可能走的是另一条通道。写一个被动观察器替代界面，直接看报文，例如订阅消息总线的脚本，见 `examples/ws_probe.py`。

## 给静默失败加观测点

链路里没有日志的分支最危险：判断不成立、catch 吞掉异常、提前 return，三种都不会留痕。

做法：跑测之前先扫一遍相关代码，找到这类分支，临时加打印（带上判断依据的实际取值），跑完场景后删掉。打印内容要包含参与判断的原始值，只打一句"跳过"没用。

## 场景参数化

一次只测正常路径不够。把故障与边界做成开关，逐档跑：

- 成功。
- 对端返回失败（业务错误码）。
- 对端返回参数非法（校验错误，且带上错误详情）。
- 对端不返回（挂起），配合把被测方的超时阈值临时调小，例如从 1800 秒调到 10 秒，否则等不起。
- 对端连不上（桩不起）。
- 边界值：空值、0、负值、超长、格式非法。

边界值靠桩的状态设置来构造，别改被测代码。

## 预期噪音

有些报错是本地环境固有的，不是故障。跑之前先列出来，否则下一轮排查会当成问题：

- 二进制协议通道连不上：本地没有对端，连接被拒或被判解码错误，属正常。
- 云端或第三方不可达：启动时与定时任务里的推送失败日志，属正常。
- 缺硬件：摄像头、串口、扫码枪相关报错，属正常。
- 鉴权拦截：本机不带头调某些接口返回 401，属正常。

列进结论时写清楚"哪条日志属预期、判据是什么"。

## 收尾还原清单

逐条确认，别漏：

- [ ] 停掉本次起的桩与后端进程，端口已释放（`ss -lntp` 确认）。
- [ ] 启动脚本里没有残留测试用的覆盖参数。
- [ ] 改过的配置文件已还原，用版本控制确认没有多余改动。
- [ ] 共享盘与生产配置文件 md5 未变，或改动是用户明确要求的。
- [ ] 临时加的打印已删除。
- [ ] 临时生成的数据目录、缓存、日志按需清理或保留说明。
- [ ] 结论里写清：测通了哪几层、哪些没测、哪些是预期噪音。

## 结论写法

按层给结论，不要笼统说"通了"：

```
环境：桩 A（端口 x）替服务甲，桩 B（端口 y）替服务乙，后端跑真实 dev profile。
第一层：通过，桩收到 3 次请求，方法与路径符合契约。
第二层：通过，日志顺序为 …。
第三层：通过，产物为 …；失败场景共 5 档，4 档符合预期，1 档（挂起）未测，原因是…。
未覆盖：链路末段依赖远端，本次不可达。
预期噪音：…
```
