# 拿桩把链路跑通

用户调用时带了参数：`$ARGUMENTS`

- 参数是链路或接口：从第 1 步开始。
- 参数是故障场景（模拟超时、模拟失败一类）：走第 3 步的故障注入，模式开关优先。
- 无参数：先问清要测哪条链路、判据是什么，再动手。

## 什么时候用

满足任一条就该走这套：

- 链路里有对端在本机起不来（缺硬件、缺依赖、缺运行环境）。
- 对端在远端且不可达，或者不想让测试数据落到真环境。
- 对端还没实现，手上只有接口文档或调用方的代码。
- 只想验链路的中间段通不通，不想跑端到端。

反例：各端本机都能真跑时不做桩，直接跑真的。桩会把真实问题盖住。

## 六步法

### 第 1 步：划清各端，逐端判断能不能真跑

把链路拆成端，逐端问"本机是否具备真跑条件"：产物齐不齐、依赖装没装、硬件在不在、外部服务可达不可达。只有答否的端才做桩。把判断结果与理由写成一句话清单给用户过目，不要默默决定。

能真跑的部分越真实越好：后端能跑就跑真后端，桩只补缺口。

### 第 2 步：从被替换方的源码里抄契约

契约从调用方与被替换方的源码里抄，不要凭空编。逐条落出来：

- 方法、路径，注意尾斜杠是否敏感。
- 请求体字段名与值的格式：字符串还是数字、保留几位小数、是不是二次编码的 JSON 字符串、时间格式。
- 成功形状与失败形状，两种都要，含错误码与错误字段名。
- 状态推进与幂等点：对端会不会按序号、id 或时间去重。

清单模板与检查点见 `references/contract-first.md`。

### 第 3 步：写桩

规矩：

- 优先纯标准库，别为了起桩再装一套依赖。
- 只实现被测方真正会调到的路由，其余一律兜底 404，并带可读消息写明"桩未实现"。缺了这句，"桩没实现"会被误判成"链路断了"，白查一轮。
- 故障场景做成命令行开关，不要靠临时改代码：成功、失败、参数非法、挂起不返回，各来一档。
- 收到请求打一行日志（含方法与路径），返回前再打一行（含状态码与结果）。日志是第 5 步验证的依据。
- 桩要能改状态：内存里存当前值，允许用查询参数或子命令设置，便于构造边界值。

模板：`examples/http_stub.py`（路由表、成功与失败、兜底 404、状态设置），`examples/cloud_stub.py`（假上游，按请求内容决定下发什么指令）。

### 第 4 步：把被测端的地址指到桩上

按影响面从小到大选手段，能用命令行覆盖就不改文件：

1. 脚本自己的命令行参数。
2. 应用的启动参数，例如 Spring 的 `--some.path=...`。
3. 前端开发代理的 target。
4. 应用配置文件。

改文件之前先记录原值，收尾要还原。共享盘与生产配置不要就地改，用只读副本加参数指向副本。细节见 `references/take-over.md`。

### 第 5 步：观测验证，分三层

1. 桩活着：端口在听，请求日志打出来了。
2. 被测端认账：日志里出现该链路的关键字，顺序符合预期。
3. 落地产物正确：文件内容、接口状态、库里字段、广播消息。

链路里没有日志的分支（判断语句、catch 块）先临时加打印再跑，测完删掉。界面不方便看时，写一个被动观察器替代界面，例如订阅消息总线的脚本，见 `examples/ws_probe.py`。起停与验证脚本模板见 `examples/sim_run.sh`。

### 第 6 步：收尾还原

停桩、还原改过的配置、核对共享文件没被动过、删掉临时打印、把"预期噪音"写进结论。清单见 `references/verify-and-cleanup.md`。

## 三条硬规矩

1. **契约从源码抄**，失败分支与成功分支同等对待。
2. **桩只补缺口**，本机能真跑的端不许用桩替。
3. **不碰共享与生产文件**，改用副本加参数指向。

## 常见坑

端口占用、就绪探测只看端口有没有人听、静默失败分支、单连接服务互相顶替、对端按序号去重导致第二轮测试不生效、管道提前退出导致误判、产物比源码旧、系统代理拦掉本机请求。逐条的症状与做法见 `references/pitfalls.md`。

开工前先过一遍这份清单，能省一轮返工。
