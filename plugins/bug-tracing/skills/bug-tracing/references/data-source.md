# 数据源排查与连库取证

代码逻辑排除干净之后才走这一步。数据库是排查手段，不是第一步。

## 数据源疑点清单

- **脏数据。** 字段为空、超出范围、格式不对（本该是数字的存成字符串、小数位数与预期差一位）。
- **重复数据。** 同一业务主键有多条记录，取到了第一条却不是想要的那条。
- **软删除。** 查询没带删除标记，把已删的取回来；或者反过来，把正常的当已删处理。
- **数据没同步。** 上游还在写，读到的是旧值；同步任务失败或延迟。
- **多数据源。** 写进一个库，读的是另一个库（历史库、只读副本）。
- **精度与单位。** 库里存的是万元，代码按元算；库里存的是分，代码按元算。
- **时区与时间格式。** 库里是 UTC，代码按本地时间比较；日期只存了年月日，比较时却带上时分秒。
- **空值与默认值。** 库里是 NULL，代码按空字符串处理；字段有默认值，插入时被自动填了别的。
- **编码与字符集。** 中文乱码、emoji 被截断、全角半角混用导致匹配不上。
- **缓存与库不一致。** 库改了，缓存没失效，或者反过来。

## 连库取证流程

1. **先问三项**：库环境（开发、测试、生产）、库名、数据库类型（虚谷、MySQL）。三项缺一项都不动手；生产库另需用户明确许可。
2. **只读。** 只跑 `SELECT`。`UPDATE`、`DELETE`、DDL 与存储过程调用一律停下问用户，未获允许不执行。
3. **带 `LIMIT`。** 取那几条就够，不要 `SELECT *` 拉全表。
4. **按问题取。** 先按业务主键或时间范围取目标记录，再顺着关联表补证。一次只查一处，查完记下来再查下一处。
5. **记证据。** 执行的 SQL 与返回的关键几行留在会话里，结论引用它们，不要只写"查过了"。
6. **不取敏感字段。** 手机号、身份证、详细地址不出现在结果里；需要比对时只看位数或掩码。
7. **收尾。** 只读不产生副作用；不建临时表，用过连接就断开。

## 写 SQL 前先确认库类型

虚谷与 MySQL 在分页、日期函数、空值函数、字符串拼接与系统表上写法不同，照一种写另一种会直接报错。拿不准就先问用户，不要按记忆写。

## 结论里要写清的三件事

- 查的是哪个库、哪张表、哪几条记录（给主键或时间范围）。
- 数据的实际值是什么，与代码期望的差在哪。
- 这一处数据不对，是数据源本身的问题，还是上游写入时就错了。
