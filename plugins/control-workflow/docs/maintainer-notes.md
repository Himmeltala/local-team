# 维护笔记

README 只讲插件是什么、怎么装、怎么用。这份文件放维护者的东西：内部判据、改动时要跑什么。

## 提交信息格式的依据

前缀与半角冒号取自 `svn log` 实例；**单行、简短**是团队现行规定，历史提交里的多行正文是旧做法。

**评审多行正文这条判据时不要心软。** 写 git 闸门之前跑过一次对照：让一个没有技能约束的子代理在临时仓库里「把改动提交一下」，它写出的信息是「一行标题，加一个空行，再加两条 `-` 列表」，理由是"这次改动包含两件事"。这就是单行规则要防的行为，出路是拆成多次提交，不是放宽格式。

细则正文在 `skills/svn-commit/references/commit-message-format.md`，SVN 与 git 共用一份，`git-commit` 技能引用它而不是另抄。改格式只改这一个文件。

## 调整约定

- 会话常驻提醒的正文在 `hooks/session-rules.txt`，保持简短——每次会话都会占用上下文。当前 659 字符。上限是 10000 字符，超了会被换成文件路径加预览，等于失效。
- 提交闸门分两份：SVN 的 `hooks/scripts/svn-commit-guard.sh`，git 的 `hooks/scripts/git-commit-guard.sh`，两份都在 `hooks.json` 的 Bash matcher 里注册，各自独立判定，互不干扰。两份都只拦不改，工作副本始终由助手按提示手工处理。
- **SVN 闸门**三条判据：落后与冲突靠 `svn status --xml -u` 的两个元素——`item="conflicted"`（含树冲突）和 `<repos-status>`（落后服务器），后者只在远端与本地真的有差异时才出现，本地 `add` / `delete` / 改内容都不会产生，所以不会误拦正常提交；范围括号只看命令行文本。
- **git 闸门**五条判据：范围括号、信息不是单行（信息源计数大于一、引号跨行、`-F` 文件多行、`-F -`）、没给信息（非交互下会打开编辑器）、detached HEAD、落后或分叉于远端。落后判定用 `git ls-remote` 而不是 `git fetch`——ls-remote 只读远端引用，不改本地状态，钩子不动工作副本这条底线不能破；远端不可达时跳过这条，不误拦。detached HEAD 在变基、摘樱桃、合并进行中会放行，那几种状态下 HEAD 本来就是游离的。落后与分叉的提示按工作区是否干净给步骤：有未提交改动时先给 `git stash push -u`，否则 `git pull --rebase` 会被 git 以索引含未提交变更为由拒绝（这条是实测踩出来的，见下条）。
- 信息格式的判据锚行首（`^(type)[[:space:]]*\(`），所以描述里的半角括号（`fix: 统计接口(含下级)补齐`）和全角括号不受影响。命令行切段要按引号状态切：引号没闭合时换行属于信息本身，得留在同一段里，否则多行信息会被切成两段漏判；段与段之间用 NUL 分隔，按行读会把跨行段重新切开。
- 误拦是比漏拦更坏的故障——写判据时先想清楚这点。git 侧有意不拦这几类：自己仓库里 `git commit --amend` 后再强推、提交时带着未跟踪文件、`git commit -a` 把已跟踪的改动一并提交。
- 闸门解析钩子输入依赖 `python3`，退而求其次用 `jq`，两者都没有时**静默放行**。这是有意的取舍：钩子是加在提交路径上的，它自己出故障不能把人堵在提交外面。要确认闸门在不在，直接喂一条假输入试：`echo '{"tool_name":"Bash","cwd":"<工作副本>","tool_input":{"command":"git commit -m x"}}' | bash hooks/scripts/git-commit-guard.sh; echo $?`，落后或游离 HEAD 时应当得到 2；把 `-m x` 换成 `-m "feat(a): x"`，在干净仓库里也应当得到 2。
- 改闸门判定逻辑后跑对应那份验收测试：`bash tests/svn-commit-guard.test.sh hooks/scripts/svn-commit-guard.sh`（在 `/tmp/svnguard` 下重建临时版本库，31 个用例）与 `bash tests/git-commit-guard.test.sh hooks/scripts/git-commit-guard.sh`（在 `/tmp/gitguard` 下重建裸仓库与三个克隆，47 个用例）。两份都不碰真实工作副本，建库阶段任何一步失败会直接中止并报 `FIXTURE`，不会带着坏 fixture 跑出假绿。
- 钩子输入解析那段在两份闸门里是重复的，有意不抽公共库：抽了要动已经在跑、且有测试覆盖的 svn 闸门，收益不抵风险。
- 钩子用纯文本 stderr 输出拦截理由（exit 2），SessionStart 用纯文本 stdout 注入上下文。Claude Code 对 SessionStart 事件会把 plain stdout 注入上下文（官方 hooks 文档 exit-code-0 一节）；输出以 `{` 开头会被当 JSON 解析，所以正文里不要让第一行以 `{` 开头。
- **技能文档改动前先让一个子代理照着文档实际走一遍**，这是抓文档漏洞比自查更有效的办法。写 git 闸门时跑过一轮合规验证，子代理照文档在临时仓库里干活，报回三处文档自身的毛病，都已补进 `git-commit` 技能：一是「有钩子兜底」这话在没装插件的环境里是假的，现在写明了闸门是插件级钩子、不是 `.git/hooks`，`ls .git/hooks` 判断不出来；二是流程顺序走不通——落后且有未提交改动时 `git pull --rebase` 会被 git 直接拒绝，原文没交代先 `git stash push -u`；三是解冲突那节只说语义冲突要问用户，同一行两边改成不同取值的文本冲突同样是取舍题，现在给了判据（两侧内容能不能共存）。
- 子代理那轮还报了一条口径问题：文档要求「提交前把信息给用户过目」，在无人值守的执行方式下做不到。现在写成：用户不在场时按仓库历史与改动内容自定一行，提交后在报告里原样写出并说明是自行定的。
- 新增约定条目时先核对存量代码，确认是"团队实际这么干"再写进去。写进插件的规则会被当成事实执行。
