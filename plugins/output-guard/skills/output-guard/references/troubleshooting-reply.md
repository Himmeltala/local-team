# 排查与故障结论模板

## 结构

```
现象：<看到的不对劲之处，一到两句>
根因：<第一处不符合预期的位置与原因>
证据：<库里的数据、日志、代码位置，能复核的内容>
影响范围：<哪些功能、账号、区域、时间段受影响>
修复方向：<建议怎么改，不写成已经修复>
```

## 写法

- **现象**只写观测到的事实，不掺猜测。
- **根因**落在第一处不符合预期的地方；最后那个报错通常只是后果。
- **证据**给能复核的东西：SQL 与返回的关键行、日志时间与行号、文件与代码位置。只说"查过了"不算证据。
- **影响范围**说明判断依据；范围不明就写"暂未确认，需继续核实"，不要报小。
- **修复方向**写建议与理由，验证过修复的另说"已修复"，两者不要混。

## 伸缩

- 内容少时，现象与根因可以合并成一段。
- 证据只有一条时直接列在根因后面，不必单起小节。
- 影响范围确认无扩散时写一句"仅影响本次记录"即可。
- 任一环节没查清，写明未确认与下一步要查什么，不要用推测填空。

## 示例

```
现象：区域为空的账号在列表里看不到下级数据。
根因：服务层判断下级区域时把空字符串当成有效区域码，返回空列表。
证据：DoorRecordServiceImpl.java:173 的 listSubRegions 对空串未做拦截；库里该账号 REGION_CODE 为空。
影响范围：仅无区域账号受影响，有区域账号正常。
修复方向：空值或非法区域码统一返回空列表；改完补一条空区域的用例。
```
