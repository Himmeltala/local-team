# 代码改动说明模板

## 结构

```
改了什么：<文件与行为的变化>
为什么改：<需求或问题的原因>
影响范围：<受影响的接口、页面、数据、调用方>
验证方式：<实际跑过的命令与结果；没跑的写明未执行及原因>
```

## 写法

- **改了什么**按行为写，不逐行复述 diff。列出改动的文件路径，说明改动后的行为。
- **为什么改**写需求的来由或问题的根因，一句话能说清就不展开。
- **影响范围**包括接口出入参变化、数据库字段变化、调用方需要跟着改的地方。没有扩散就明说。
- **验证方式**只写实际执行过的：命令、测试、页面操作与结果。没执行就写"未执行"及原因，不要写成已验证。

## 伸缩

- 只改一个文件、一个方法时，四节可以并成两段：一段写改动与原因，一段写影响与验证。
- 多个文件同属一个改动时，按行为归并，不要按文件逐个列。
- 验证未执行时，影响范围要写得更清楚，方便他人判断风险。

## 示例

```
改了什么：区域查询为空时直接返回空列表，不再走全表条件；涉及 DoorRecordServiceImpl。
为什么改：空区域串被当成有效区域码，导致无区域账号查询结果为空。
影响范围：只影响区域为空的账号，接口出入参不变。
验证方式：未执行构建与测试，用户自行发起。
```
