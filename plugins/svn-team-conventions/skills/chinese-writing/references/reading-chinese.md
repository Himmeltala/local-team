# 读中文需求

写中文的规矩在 `SKILL.md`。这份讲另一半：读中文时怎么不误解。

中文的省略比英文多——主语、宾语、量词、连词都可能不出现，靠语境补。助手常见的错法是用英文语序去反推，或者把省略当成"意思很明显"直接开工，结果做出来的东西不是对方要的。

## 一、先补出省略的成分

中文指令常省主语与宾语。

| 原话 | 缺什么 | 处理 |
|---|---|---|
| 改一下 | 改哪儿、改成什么 | 先问，或复述你理解的改动点让用户确认 |
| 优化一下 | 优化什么指标 | 问清是速度、体积还是可读性 |
| 顺手清理一下 | 范围到哪儿 | 按插件规则默认，范围超出时先报 |
| 看着办 | 判断标准 | 给两三个方案让用户选，不要自己定 |
| 不对 | 哪儿不对 | 问具体现象，不要猜着改 |

**复述确认优先于猜测。** "你的意思是把 xxx 改成 yyy，范围只限 zzz，对吗？" 这一句比做错再返工便宜得多。

## 二、一词多义先对齐

同一个词在本团队的语境里可能有几个意思。动手前确认指的是哪一个：

| 词 | 可能的含义 |
|---|---|
| 接口 | HTTP 接口、Java interface、第三方接口 |
| 清理 | 删注释、删无用文件、清数据库 |
| 提交 | git commit、svn commit、提交表单 |
| 表 | 数据库表、前端表格、Excel 表 |
| 版本 | 版本库、软件版本、插件版本 |
| 字段 | 数据库列、Java 属性、前端表单字段 |
| 上线 | 部署到测试环境、部署到生产环境 |

用户所在的项目与目录能打消大部分歧义（在 `~/projs` 下的 SVN 工作副本里说"提交"，就是 svn commit）。**上下文不够时问，不要挑一个先做。**

## 三、条件在前，结论在后

中文习惯先铺条件、再给结论："工作副本落后就别提交"、"太大就拆开"。这是正常语序，不是倒装，不要反过来读成"提交前必须落后"。

同样地，"A 不是 B 的" 与 "A 不是 B" 意思不同，"除了 A 都行" 与 "A 除外也行" 相反。这类句子读第二遍，别看开头就下结论。

## 四、否定词漏读代价最大

不、别、禁、免、除非、勿、无需、不必——漏掉一个，整个需求反过来。

- 含否定词的需求，动手前把否定部分单独复述一遍。
- "不" 与 "否" "非" "无" 一起出现时逐字读（"不可省略" ≠ "可省略"）。
- 双重否定当肯定读，但写完要验回原句（"不禁止" 是允许，"不是不允许" 也是允许，程度不同）。

## 五、一次问一个

一次只问一个问题。把三四个问题摞在一条消息里，用户只回答最后一个，前面的变成你替他决定的。

问题要带选项与你的判断，不要空手问："范围是只改这个文件，还是连同同目录的其它文件一起？我建议只改这个文件，因为 diff 更小。"

## 六、承诺范围照字面执行

用户说的范围就是范围。"顺手清理注释" 意味着本次编辑碰到的文件，不意味着整目录；"先看下" 是只读，不是先改一半。**扩展范围要先问**，哪怕方向看起来明显正确。

## 七、中文语气不用当模糊信号

"你看着办吧""大概""差不多""应该可以" 是留余地，不是授权扩大范围。这类词出现时，按最小改动做，并在回报里说明你按什么理解做的，让用户有机会纠正。
